# Lockfile

`alai lock` resolves the project's manifest against its indexes and writes
`alai.lock` beside the project's `alai.toml`; `alai sync` installs
exactly what it lists ([install.md](install.md)). The format is read and written by `src/alai/_lock.py`,
resolution is in [resolver.md](resolver.md). The user documentation is
`docs/managing-collections.md#locking`.

## The format

A playbook project's `alai.toml` and the lock `alai lock` writes for it:

```toml
# alai.toml
link_mode = "hardlink"                   # settings: not part of the lock

[[index]]
name = "internal"
url = "https://ansible-index.corp.example/"

[project]
collections_dir = "collections"          # a project-only setting: not part of the lock either
requires_ansible = ">=2.17"
collections = ["community.general>=9,<11", "ansible.windows", "corp.tools>=1.2"]

[project.groups.test]
collections = ["ansible.posix"]

[project.overrides]
"ansible.netcommon" = ">=6"
ignore_requires_ansible = ["corp.tools"]

[project.sources]
"corp.tools" = { index = "internal" }
```

```toml
# alai.lock
# This file is generated by `alai lock`. Don't edit it by hand: any changes,
# comments included, are lost the next time alai writes it.
version = 1
revision = 1

[overrides]
"ansible.netcommon" = ">=6"
ignore_requires_ansible = ["corp.tools"]

[sources]
"corp.tools" = { index = "internal" }

[project]
requires_ansible = ">=2.17"
collections = ["community.general>=9,<11", "ansible.windows", "corp.tools>=1.2"]
groups.test.collections = ["ansible.posix"]

[[collection]]
name = "ansible.netcommon"
version = "8.7.1"
source = { index = "https://ansible-index.corp.example/" }
cksum = "3b1f…"
size = 1204812
requires_ansible = ">=2.16.0"
dependencies = ["ansible.utils"]

[[collection]]
name = "community.general"
version = "10.7.2"
source = { index = "https://index.alai.sh/" }
cksum = "5459…"
size = 2913455
requires_ansible = ">=2.16.0"
dependencies = ["community.library_inventory_filtering_v1"]

[[collection]]
name = "corp.tools"
version = "1.4.0"
source = { index = "https://ansible-index.corp.example/" }
cksum = "e1fb…"
size = 84213
requires_ansible = ">=2.15,<2.18"        # ignored for corp.tools, as alai.toml asks
dependencies = ["ansible.netcommon"]

# ...ansible.posix, ansible.utils, ansible.windows and
# community.library_inventory_filtering_v1 the same way
```

| Key | |
|---|---|
| `version` | The lockfile format. A lock with a higher `version` than this alai reads is an error asking for a newer alai |
| `revision` | Additions to the format an older alai can safely ignore. Any value is read; a missing one is 0. alai writes its own |
| `overrides` | `alai.toml`'s `[project.overrides]`, as written: one set for the whole resolution |
| `sources` | `alai.toml`'s `[project.sources]`, as written (index names, not URLs): also resolution-wide |
| `project` | The project as a root of the resolution: its `requires_ansible`, `collections` and `groups.<name>.collections`, as written in `alai.toml` |
| `collection` | One entry per locked collection, sorted by name |
| `collection.name`, `.version` | What's installed |
| `collection.source` | Where it comes from, as a table naming the kind: `{ index = "<index root URL>" }`, or a directory or tarball (see [Other sources](#other-sources)) |
| `collection.cksum`, `.size` | The artifact's sha256 and size, from the index or the tarball; not for a directory |
| `collection.collections` | A directory's `galaxy.yml` dependencies when it was locked, so a change to them makes the lock stale, or a tarball's `MANIFEST.json` dependencies, so locking again needn't download it; not for an index's |
| `collection.requires_ansible` | The version's own `requires_ansible`, as the index gives it; absent when it has none |
| `collection.dependencies` | The names of the locked collections it depends on, sorted |

What `alai sync` installs is the closure of the roots' requirements, through
each entry's `dependencies`, plus the groups asked for. A root needs no
`dependencies` of its own: every requirement names a collection, so its
direct dependencies are its requirements' names.

### A collection project

Implemented on 2026-10-21 (see
[collection-development.md](collection-development.md)). The collection
itself is an entry, as a uv project with a build system is an entry with
`source = { editable = "." }` (a uv project without one is `source = {
virtual = "." }`, which alai's `[project]` table plays the part of):

```yaml
# galaxy.yml
namespace: corp
name: tools
version: 1.4.0
dependencies:
  ansible.netcommon: ">=5.0.0"
  ansible.utils: "*"
```

```yaml
# meta/runtime.yml
requires_ansible: ">=2.16"
```

```toml
# alai.toml: only what galaxy.yml and meta/runtime.yml can't say;
# [project] collections or requires_ansible here is an error.
[project.groups.test]
collections = ["ansible.posix", "community.crypto>=2"]
```

```toml
# alai.lock
version = 1
revision = 1

[project]
requires_ansible = ">=2.16"                                # meta/runtime.yml
collections = ["ansible.netcommon>=5.0.0", "ansible.utils"]    # galaxy.yml, in alai.toml's syntax
groups.test.collections = ["ansible.posix", "community.crypto>=2"]

[[collection]]
name = "corp.tools"
version = "1.4.0"                                          # galaxy.yml
source = { editable = "." }                                # the checkout, linked into the tree
requires_ansible = ">=2.16"
dependencies = ["ansible.netcommon", "ansible.utils"]

[[collection]]
name = "ansible.netcommon"
# ...
```

- **The inputs stay in `[project]`**, for both kinds of project, so
  staleness, `--locked` and `lock --check` work one way. The plan had put
  them on the root entry, as uv puts a package's on its `[package.metadata]`;
  that's for when several roots exist (a workspace), each with its own.
- **`galaxy.yml`'s dependencies are rewritten in `alai.toml`'s syntax**:
  parsed as ansible-galaxy parses them (`VersionReq.parse_index`), so a bare
  `1.0.0` is `==1.0.0` and `"*"` is dropped.
- **The root entry has no `cksum` or `size`**, as it changes with every
  edit, and its `dependencies` are its requirements' names. A change to its
  name, version or `requires_ansible` makes the lock stale, as a change to
  the requirements does.
- **`version` stays `1`** until the first release (see
  [Decisions](#decisions)). An `editable` source other than `.` is a
  [path source](#other-sources) (2026-10-22); workspaces, when they come,
  will need another way to mark their members' roots.

## Decisions

- **TOML, named `alai.lock`, beside `alai.toml`**, as `uv.lock` and
  `Cargo.lock` are. It's committed with the project.
- **`version` and `revision`, as uv has them** (decided with the user,
  2026-10-25). `version` changes when an older alai would misread the lock,
  and a higher one is refused, asking for a newer alai; `revision` changes
  for additions an older alai can safely ignore, and any value is read,
  with unknown keys ignored. alai writes its own `revision`, so an older
  alai rewriting the lock drops what it didn't know, as uv does. Tried with
  uv 0.13.5, which writes `version = 1` and `revision = 5`: `revision = 99`
  passed `uv lock --check` and `uv sync --frozen` silently, `uv lock` kept
  it when nothing changed and wrote 5 when something did, and a missing
  `revision` made `uv lock --check` fail; `version = 2` failed every
  command with `uses an unsupported schema version (v2, but only v1 is
  supported)`. A missing `revision` here is read as 0 and doesn't make the
  lock stale, since staleness is about inputs, not layout. PEP 751's
  single `lock-version = "1.0"` (error on an unknown major, warn on unknown
  keys in a newer minor) was considered: two integers say the same, follow
  uv, and are compared without parsing. A change that matters to what
  runs, such as a Python environment ([environments.md](environments.md)),
  is a `version` bump even when it only adds keys, since an older alai
  ignoring it would run the wrong thing without saying so. Both stay `1`
  until the first release, as there's no older alai to protect.
- **Requirements are named by kind**: `[project] collections` and
  `groups.<name>.collections`, as `alai.toml` names them, and a
  collection's own `collections` (2026-10-25). Both were `requirements`
  before; the index spec reserves `requirements` on a version line for
  Python and system packages, and a Python list would sit beside these as
  `python`.
- **Written deterministically**: collections sorted by name, dependencies
  sorted, one key per line in a fixed order, so a change shows up as a small
  diff. A comment at the top says it's generated.
- **Written with `toml_edit`, in a layout alai fixes** (2026-10-23, decided
  with the user; before, a small emitter in `_lock.py`). `render_lock` lays
  the lock out as a mapping and `_native.toml_dumps` writes it by fixed
  rules: `[table]`s and `[[collection]]`s after a blank line, `source` as
  an inline table with its keys in a fixed order, `groups.<name>.collections`
  as dotted keys, and an array over 80 characters one item per line. Every
  lock the emitter wrote comes out byte for byte the same; a string with a
  `"` or `\` is written as a literal string (`'a"b'`) where the emitter
  escaped it, which reads the same. Python's stdlib only reads TOML, and
  tomli-w can't write `source` as an inline table or give control over the
  layout. The layout being fixed by alai, not left to a library's
  formatting choices, keeps the bytes stable: `toml_edit` is pinned in
  `Cargo.lock` and built into each release, so two people with the same
  alai write the same lock. uv also writes `uv.lock` with `toml_edit`.
- **Each root's inputs are copied in**, so `alai sync` can tell the lock
  is out of date without resolving, and `lock --check` can tell the inputs
  changed even when the result didn't. They're
  compared after parsing (`Manifest.resolution_key`), so whitespace or
  reordering in `alai.toml` doesn't make the lock stale; requirements compare
  as sets.
- **`alai lock`** loads the settings and `alai.toml`, resolves with the
  current `alai.lock` as the preference, and writes the lock atomically, as
  `uv lock` does. An unchanged result leaves the file untouched, and a failed
  resolution leaves the lock untouched. `-U` / `--upgrade` and `-P` /
  `--upgrade-collection NAME` drop the locked preference for every
  collection or the named ones, as uv's `-U` and `-P` do, on `lock`,
  `sync`, `add` and `remove` alike. The short flags are uv's, so the habit
  carries over; the long one says "collection", the word alai uses
  everywhere else, rather than uv's `--upgrade-package`, and isn't kept as
  an alias since nothing is released.
- **`--upgrade-group NAME`** (asked for 2026-10-20), on `lock`, `sync`,
  `add` and `remove`, is `-P` for every collection group `NAME` lists in
  `alai.toml`, as uv's `--upgrade-group`. Tried with uv 0.13.0 on
  2026-10-21, with everything locked old and the requirements then
  loosened: `uv lock --upgrade-group test` upgraded what `test` lists
  (`requests`, `attrs`) and nothing they depend on (`idna` stayed at 3.4,
  `urllib3` at 1.26.20), and a package the group shares with the project
  (`six`, through group `lint`) was upgraded for both, as the lock has one
  version of it. It can be repeated and combined with `-P`. A group
  `alai.toml` doesn't have is an error before resolving, as uv's "Group
  `nope` is not defined in the project's `dependency-groups` table", here
  worded as `sync --group`'s is (`--upgrade-group: alai.toml has no group
  'nope' (it has 'test')`). The project's own collections aren't a group
  for it, as uv's dependencies aren't; `-U` or `-P` covers them. It's not on
  `collection install`, as uv 0.13.0 lists it in `uv pip install --help` but
  refuses it, with or without `--group`: "`--upgrade-group` is not supported
  in `uv pip` commands". For `add` and `remove` the group is read from
  `alai.toml` as edited (`_project.Upgrade`).
- **`-U` works with `lock --check` and `--locked`**, on `sync`, `add` and
  `remove` alike (decided 2026-10-21): it fails only if the upgrade would
  change `alai.lock`, so it checks that the lock already has the newest
  versions that fit. uv 0.13.0 rejects `--upgrade` with `uv lock --check`,
  `uv sync --locked` and `uv add --locked` ("the argument '--locked' cannot
  be used with '--upgrade'"), though it takes `-P` with them. alai allows
  both, the same on every command: an upgrade that leaves the lock as it was
  is a valid result, not a mistake.
- **`alai lock --check` resolves**, as `uv lock --check` does, and exits 1
  without writing when the lock is missing (checked first, without
  resolving) or would change: its copied inputs ask for something else than
  `alai.toml`, or the resolved collections differ, say because a locked
  version was removed from its index or its index is no longer configured.
  The change lines are printed as `alai lock` would print them, then what
  in `alai.toml` differs from the inputs the lock copied, under `alai.toml
  has changed since alai.lock was made:`, one indented line per
  difference named by its key (`project.collections: added b.b`,
  `project.requires_ansible: changed >=2.17 to >=2.18`), compared as
  parsed (`_lock.input_changes`). That's the only explanation when the
  requirements changed but every version stayed, such as listing a
  collection that was already locked as a dependency. A directory source's
  `galaxy.yml` (or a built collection's `MANIFEST.json`) and
  `meta/runtime.yml` are inputs too (asked for
  2026-10-22): under `../src has changed since alai.lock was made:`, as the
  lock writes the path, one line per difference from its entry's snapshot,
  named by file and key (`galaxy.yml version: changed 1.0.0 to 1.1.0`,
  `galaxy.yml dependencies: added d.d`, `meta/runtime.yml
  requires_ansible: changed >=2.15 to >=2.16`; `_lock.local_changes`). A
  hash of the two files in the lock was considered instead of the
  `collections` snapshot and dropped: any edit, a description or a
  comment, would make the lock stale where the resolution can't change,
  and the check couldn't say what changed. `sync`, `add` and
  `remove` with `--locked` print both the same way before their error
  (asked for 2026-10-21; `_project.report_changes`). uv prints neither:
  "The lockfile at `uv.lock` needs to be updated" alone. A plain `alai
  lock` prints only the change lines, as it always did. It connects
  to the indexes unless `--offline`. A check that only compared the files,
  without the network, was the first version (2026-10-20) and was dropped
  to follow uv: it couldn't see a removed version. That comparison stays as
  `_lock.stale()` for `sync`, which needs to decide quickly whether to
  resolve again.
- **Roots and the resolution are kept apart**, as uv does: a root's
  requirements, groups and `requires_ansible` are on the root (`[project]`
  today, `project`-source collections later), and the overrides for the
  whole resolution are `[overrides]`. `alai.toml` makes the same split:
  everything under `[project]` is the project, and `[project.overrides]`
  is only read from the root `alai.toml` once workspaces exist.
- **The project is `[project]`, not a `[[collection]]`**: a playbook project
  isn't a collection, has no name and is never installed. Kinds of thing
  have their own tables (`[[collection]]`, later `[[role]]`) rather than one
  `[[package]]` with a `type`, because a role and a collection can share a
  `namespace.name`, as Ansible's own split (`requirements.yml`'s
  `collections:` and `roles:`, `collections/` and `roles/`) reflects. `project` is a
  kind of source, so it can't collide with a collection's name.
- **One resolution for every group**, as uv does: `project.collections` and
  all `[project.groups.*]` are resolved together into one consistent set, and `sync`
  installs the groups asked for. Which collections a group needs is worked
  out from the manifest and each entry's `dependencies`, so the lock doesn't
  record group membership. A group that conflicts with the project fails
  `lock`.
- **The index is recorded by URL**, not by the name `alai.toml` gives it, so
  renaming an index doesn't change the lock and two people with different
  names for one index agree. `lock --check` also fails when an entry's index
  URL is no longer configured.
- **No download URLs.** `sync` builds them from the index's `dl` template
  and `cksum`, as Cargo does, so moving the artifact host doesn't invalidate
  locks. The index spec's client rules ask lock files to record the index,
  name, version and `cksum`; `size` lets `sync` report download sizes before
  it starts.
- **Dependencies are names.** A name has exactly one entry in a lock (one
  version per collection per environment), so the name says which. uv does
  the same: a plain `uv.lock` references a dependency as `{ name = "demo" }`,
  and only adds `version`, `source` and `marker` when the lock holds two
  entries for one package, as a forked resolution does (tested with uv 0.13:
  `demo==1.0; python_version < "3.12"` and `demo==2.0; python_version >=
  "3.12"` gave two `[[package]]` entries named `demo`, each with
  `resolution-markers`, and references carrying all three). Collections have
  no platforms, Python-version wheels or conditional dependencies, so the only
  marker alai would ever need is the ansible-core version, for the "forks"
  option in [environments.md](environments.md). If locks fork,
  `dependencies` becomes tables (`name`, plus `version` and `marker` when
  ambiguous) and entries get their ansible-core range, behind a `version`
  bump: an alai that doesn't know forks must refuse such a lock, which
  today's reader already does ("locked more than once").
- **`requires_ansible` per entry** records each locked version's own
  range, upper bounds the resolver ignored included (see
  [resolver.md](resolver.md)). It was kept for `sync` and `run` to check
  the installed ansible-core against, but ansible-core does that as it
  loads each collection ([run.md](run.md#checking-ansible-core)); it
  stays for forked locks and for what a future command may report.
- **Unknown keys are ignored when reading**, as in the index spec, so a
  newer alai can add an optional key without breaking older ones in the same
  team. `version` is bumped only for a change an older alai would misread,
  such as a new `source` kind; an unknown kind is an error asking for a
  newer alai.

## Other sources

Directories, tarballs by path or URL, and git repositories are implemented
(2026-10-22). Each is a `[project.sources]` entry in `alai.toml` and a
`source` table naming its kind in the lock, with uv's names for each kind,
since uv 0.13.0 draws the same lines:

| `[project.sources]` | `source` in the lock | Pinned by | Status |
|---|---|---|---|
| `{ index = "<name>" }` | `{ index = "<url>" }` | `cksum`, `size` | Done |
| `{ path = "<dir>" }` | `{ directory = "<dir>" }` | Nothing: `collections` re-read | Done |
| `{ path = "<dir>", editable = true }` | `{ editable = "<dir>" }` | Nothing: `collections` re-read | Done |
| `{ git = "<url>", rev = "<rev>", subdirectory = "<dir>" }` | `{ git = "<url>", rev = "<rev>", subdirectory = "<dir>", commit = "<sha>" }` | `commit`, plus `collections` | Done ([below](#git-repositories)) |
| `{ url = "<tarball url>" }` | `{ url = "<tarball url>" }` | `cksum`, `size`, plus `collections` | Done |
| `{ path = "<file>.tar.gz" }` | `{ path = "<file>.tar.gz" }` | `cksum`, `size`, plus `collections` | Done |

Tried with uv 0.13.0 on 2026-10-22: `uv add ../lib` wrote `lib = { path =
"../lib" }` to `[tool.uv.sources]` and locked `source = { directory =
"../lib" }`; `uv add --editable ../lib2` wrote `editable = true` and locked
`{ editable = "../lib2" }`. uv keeps `{ path = ... }` in the lock for an
archive file, so a directory being `directory` leaves `path` for tarballs.
The earlier plan here had `{ path = "<dir>" }` for a directory in the lock;
uv's names replaced it. `editable = "."` stays the project's own collection
([A collection project](#a-collection-project)).

```toml
# alai.toml
[project]
collections = ["corp.dev", "corp.lib"]

[project.sources]
"corp.dev" = { path = "../corp.dev" }
"corp.lib" = { path = "../corp.lib", editable = true }
```

```toml
# alai.lock
[sources]
"corp.dev" = { path = "../corp.dev" }
"corp.lib" = { path = "../corp.lib", editable = true }

[[collection]]
name = "corp.dev"
version = "0.3.0"                          # galaxy.yml
source = { directory = "../corp.dev" }
requires_ansible = ">=2.16"                # meta/runtime.yml
collections = ["ansible.utils>=2"]         # galaxy.yml's dependencies, in alai.toml's syntax
dependencies = ["ansible.utils"]

[[collection]]
name = "corp.lib"
version = "1.0.0"
source = { editable = "../corp.lib" }
collections = []
dependencies = []
```

- **What pins the content depends on the source.** An index or tarball has
  `cksum` and `size`; git has the commit (with the requested `rev`, so
  `--upgrade` can move a branch); a directory has nothing, since it's meant
  to change. `cksum` and `size` are written only when there is one.
- **A directory's metadata is a snapshot**, re-read every time. Its
  `version` and `requires_ansible` are on the entry, and its `galaxy.yml`
  `dependencies` are its `collections`, rewritten in `alai.toml`'s syntax as
  the project's own collection's are, as uv keeps a local package's
  `requires-dist` in `[package.metadata]`. `_lock.stale()` re-reads
  `galaxy.yml`, or a built collection's `MANIFEST.json` ([install.md](install.md#a-built-directory)),
  and `meta/runtime.yml` (`Manifest.local`, filled by
  `_project.read_local`) and compares them, requirements as parsed, so
  `sync` locks again, and `lock --check` and `--locked` fail, when they
  change. uv 0.13.0 did the same: after bumping `lib`'s version, `uv sync`
  locked again and replaced it, and `uv lock --check` failed. A git entry
  carries `collections` too, read from the commit, so locking again
  needn't fetch it.
- **A directory's dependencies are chosen like any other collection's**:
  their own `[project.sources]` entry, else the first index that has them.
- **A source applies to any collection in the resolution**, as an index
  pin already does, not only to what the project lists. uv 0.13.0 applies
  `[tool.uv.sources]` only to direct dependencies: with `dep` a path
  dependency needing `lib`, a `lib = { path = "../lib" }` source was
  ignored and `lib` looked for on the index. uv gives no design reason in
  its docs; asked to change it (astral-sh/uv#9446, open since November
  2024 and labelled `needs-decision`), a maintainer answered "If you're
  going to define a source, you should just make it a direct dependency --
  what's the issue with that?", and the workarounds offered are listing it
  in a dependency group or an `override-dependencies` URL. alai keeps its
  rule: one entry by name is simpler, it's what index pins already do, and
  a dependency deep in the tree can be pointed at a checkout to try a fix
  without listing it. Checked 2026-10-22; see
  [user-questions.md](user-questions.md).
- **The name must match**: the directory's `galaxy.yml` must be for the
  collection its entry names, as uv refused `foo @ ./lib` ("Package
  metadata name `lib` does not match given name `foo`"). The project's own
  collection can't be given a source; it's always the checkout. Any
  source for it is an error, an `index` or `url` one included, checked
  before anything is read or downloaded. uv 0.13.5 silently ignores a
  `[tool.uv.sources]` entry for the project itself, even a `path` or an
  index that isn't configured; alai refuses instead, as an entry that's
  written down but never used is easy to misread.
- **Paths are as written**: relative to the project root, or absolute,
  with `~` expanded, as uv writes an absolute path it's given as absolute.
- **Only the project's own manifest can name these sources.** A
  `galaxy.yml` lists dependencies by name and version only, so a
  dependency can't pull in a git URL or a local path.

### Tarballs

Implemented on 2026-10-22. A path to a file, rather than a directory, is a
built collection's tarball, as uv tells an archive from a directory on
disk, and `{ url = ... }` downloads one:

```toml
# alai.toml
[project.sources]
"corp.net" = { path = "dist/corp-net-2.1.0.tar.gz" }
"corp.web" = { url = "https://artifacts.example.com/corp-web-1.4.0.tar.gz" }
```

```toml
# alai.lock
[[collection]]
name = "corp.net"
version = "2.1.0"                          # MANIFEST.json
source = { path = "dist/corp-net-2.1.0.tar.gz" }
cksum = "9c1e…"
size = 48213
requires_ansible = ">=2.16"                # meta/runtime.yml, in the tarball
collections = ["ansible.utils>=2"]         # MANIFEST.json's dependencies
dependencies = ["ansible.utils"]
```

Tried with uv 0.13.0 on 2026-10-22, with an sdist on disk and served by
`python -m http.server`:

- **The lock records the archive's hash**: `source = { path =
  "../dist/lib-0.1.0.tar.gz" }` or `{ url = "http://…" }`, with `sdist = {
  hash = "sha256:…" }`. Here that's `cksum` and `size`, as an index's
  artifact has, and the `collections` snapshot a directory has, so a URL
  entry carries everything the resolver needs without the tarball.
- **A URL is downloaded once.** With the file behind the URL rebuilt, `uv
  lock`, `uv lock --check` and `uv sync` all passed on the cached copy; with
  an empty cache, each failed on the hash ("Hash mismatch for `lib @ …`").
  alai does the same: `read_archives` (`_project`) takes a URL locked from
  the same URL from the lock entry, without downloading it, and `sync`
  checks the download against `cksum` and `size` as for an index's. `-U`
  or `-P` downloads it again. uv also takes its own cache's copy for the
  URL; alai's cache is keyed by checksum, which the URL alone doesn't
  give, so a URL that isn't locked is downloaded every time it's locked.
- **A file that changed is an error until `-P`.** With the file rebuilt
  at the same path, `uv sync`, `uv lock`, `uv lock --check` and even `uv add`
  of the same file failed on the hash; `uv lock -P lib` locked the new one,
  and `uv sync` then replaced it (`~ lib==0.1.0`). alai hashes the file on
  every command that reads the project (`read_local`; 2 ms for a 3 MB file,
  the size of community.general's, measured 2026-10-22), so `stale()` sees the change, and `read_archives`
  stops with the error, naming `alai lock -P`. Locking again on its own,
  as a directory does, was considered: the checksum is there so the lock
  says exactly what's installed, and a file swapped under the same name,
  from another build or by a teammate, is what it should catch. See
  [user-questions.md](user-questions.md#a-tarball-that-changed).
- **`url` is `http` or `https`**, as uv refused a `file://` URL in
  `[tool.uv.sources]` ("URL scheme is not allowed"): a file is a `path`.
  uv also requires the URL to end in an archive extension, as it picks the
  format from it ("Expected direct URL … to end in a supported file
  extension"); alai has one format and reads it from the content, so any
  URL will do, such as one with a query string.
- **Only gzip** (decided with the user, 2026-10-22), as every collection
  build writes: a tarball source must start with gzip's magic bytes, `1f
  8b` (RFC 1952), checked before a file is read and on a URL's first chunk,
  so an error page served with a 200, or a large file of something else,
  isn't downloaded whole (`GZIP_MAGIC`; `Fetcher.download`'s `magic`).
  `tarfile`'s `r:*` could read plain, xz or bzip2 tarballs too, as
  ansible-galaxy's `tarfile.open(mode='r')` does; allowing them later is
  only dropping the check. Tar's own `ustar` marker is 257 bytes into the
  decompressed stream, so it can't be checked as cheaply; a gzip file that
  isn't a tarball fails when it's read.
- **What's in it is read from its `MANIFEST.json`**, as ansible-galaxy
  reads a tarball's (`_get_meta_from_tar` in ansible-core 2.21.5's
  `concrete_artifact_manager.py`), from the copy extracted into the
  artifact cache, so the cache holds it before `sync` needs it.
  `meta/runtime.yml` gives `requires_ansible`, as for a directory. It must
  be the collection its entry names.
- **`ansible-galaxy` downloads a URL with no checksum** (`_download_file(…,
  expected_hash=None)`, "URLs don't support checksums"), and takes any
  existing file as a tarball (`_is_file_path`). alai pins both by checksum,
  which is the point of the lock.

How each is installed is in [install.md](install.md#directory-and-editable-sources)
and [install.md](install.md#tarball-sources).

### Git repositories

Implemented on 2026-10-22 (`GitSource` in `_manifest.py`, `GitCommitSource`
in `_lock.py`, `read_git_sources` in `_project.py`). How a commit is fetched
and installed is in [install.md](install.md#git-sources).

```toml
# alai.toml
[project.sources]
"corp.net" = { git = "https://git.example.com/corp/net.git", rev = "v2.1.0" }
"chocolatey.chocolatey" = { git = "https://github.com/chocolatey-community/chocolatey-ansible", rev = "1.5.0", subdirectory = "chocolatey", version = "1.5.0" }
```

```toml
# alai.lock
[[collection]]
name = "chocolatey.chocolatey"
version = "1.5.0"                          # the source's version, galaxy.yml's is a placeholder
source = { git = "https://github.com/chocolatey-community/chocolatey-ansible", rev = "1.5.0", subdirectory = "chocolatey", commit = "e1c6b3787307ad08e0f84d9b2fc8965471b264d9" }
requires_ansible = ">=2.10.0"              # meta/runtime.yml, at the commit
collections = []                           # galaxy.yml's dependencies, at the commit
dependencies = []
```

Tried with uv 0.13.0 on 2026-10-22, against github.com:

- **`uv add "git+<url>@<rev>#subdirectory=<dir>"`** wrote `{ git = "<url>",
  subdirectory = "<dir>", rev = "<rev>" }` to `[tool.uv.sources]`, and
  locked `source = { git = "<url>?subdirectory=<dir>&rev=<rev>#<sha>" }`.
  alai keeps the separate keys it planned, as its other `source` tables
  have, with uv's names; the meaning is the same.
- **The commit is resolved from `rev`** and the lock is what's installed;
  `rev` is kept so `-U` and `-P` can move a branch.
- **uv's GitHub fast path**: for a github.com URL, `uv lock` asked
  `api.github.com/repos/<owner>/<repo>/commits/<rev>` for the commit and
  read `pyproject.toml` from `raw.githubusercontent.com`, so it locked
  without running git; git ran only to install. alai could do the same for
  `galaxy.yml` and `meta/runtime.yml`; it's only faster, so it's left for
  later.

ansible-galaxy writes the same thing as
`git+<url>#/<subdir>,<rev>`: `parse_scm` in ansible-core 2.22.0rc1's
`galaxy/collection/concrete_artifact_manager.py` takes the fragment as the
directory and what follows the comma as the version to check out. When
that directory has no `galaxy.yml` or `MANIFEST.json`, it installs every
collection one level below it (`_find_collections_in_subdirs` in
`galaxy/dependency_resolution/dataclasses.py`).

- **`subdirectory` is explicit.** A `[project.sources]` entry names one
  collection, so there's no scan for several; when the repository's root
  isn't a collection, the error lists the directories below it that are.
  The checkout is the whole commit, so collections from different
  directories of one commit share it.
- **The name must match**, and only the project's manifest can name a git
  source, as for a directory ([above](#other-sources)).

### A version that isn't one

Decided with the user on 2026-10-22: a directory or git source whose
`galaxy.yml` has no usable version is an error unless the source gives
one, `version = "<semver>"`, which the lock then records and a build
writes into `MANIFEST.json`. `alai add` writes it for a git URL given with
`#version=<semver>` ([install.md](install.md#git-sources)); a directory's
is added by hand (decided with the user, 2026-10-22). uv 0.13.0 reads a
`#` part on a plain path too (`uv add ../lib#subdirectory=.` added
`../lib`), which keeps a directory with a `#` in its name from being
given as one (`../odd#dir/lib2`: "Distribution not found"); a directory
whose `galaxy.yml` has a placeholder is usually one being worked on,
better linked editable with its version written once in `alai.toml`. A
`file://` URL with a `#` part, which uv ignores (`#egg=x` was dropped),
is an error, so it isn't installed as something other than what was
asked for. Some repositories keep a placeholder their
release script fills in: chocolatey-ansible's `galaxy.yml` has `version:
'{{ REPLACE_VERSION }}'` at every commit.

- **Only where the version comes from `galaxy.yml`**: a `path` source that's
  a collection's source, plain or editable, and a git source. An index's
  artifact, a tarball, and a built directory have a `MANIFEST.json` written
  by a build, which checks the version, so `version` on those is an error,
  as it is for a git repository whose commit holds a built collection,
  read when it's locked. Errors and warnings name a commit's files as
  `<url>@<commit>`, not where they are in the cache.
- **ansible-galaxy accepts `null`, `''` and `'*'`** as version `*`, which
  satisfies any requirement, and writes `"version": "*"` into
  `MANIFEST.json`; it rejects a missing version and other strings such as
  `'1.0'` or `'main'` ("A SemVer-compliant version or '*' is required"),
  and crashes on `'{{ REPLACE_VERSION }}'` (`Non integer values in
  LooseVersion`), so it can't install chocolatey from git either (tried
  with `ansible-galaxy collection install <dir>`, ansible-core 2.22.0rc1).
  alai rejects all of these today (`read_collection_dir`), and keeps doing
  so: a collection counted as any version would satisfy a requirement it
  doesn't, and other collections' requirements on it would mean nothing.
- **Python has no versionless package**: core metadata requires `Version`,
  and pip 24.1+ and uv reject one that isn't PEP 440. Where Python allows
  `dynamic = ["version"]`, the build works it out (setuptools-scm from `git
  describe`); a collection has no build step alai could run, as
  chocolatey's is its own script. uv's nearest override is
  `[[tool.uv.dependency-metadata]]`, which supplies a package's version and
  dependencies when they can't be read.
- **Not chosen**: counting an unusable version as `*`, as ansible-galaxy
  does, and taking the version from a tag that points at the locked commit.
  Either can be added later; an explicit version is the one that's never
  wrong without the user saying so. See
  [user-questions.md](user-questions.md#a-source-with-no-usable-version).

- **The source's `version` wins** over a valid one in `galaxy.yml`, with a
  warning naming both (decided with the user, 2026-10-22): like a source
  itself, it's an override, and the warning catches one left behind after
  the repository fixed its version.
