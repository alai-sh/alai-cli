# Lockfile

`alai lock` resolves the project's manifest against its indexes and writes
`alai.lock` beside the project's `alai.toml`; `alai sync` (slice 4) installs
exactly what it lists. The format is read and written by `src/alai/_lock.py`,
resolution is in [resolver.md](resolver.md). The user documentation is
`docs/projects.md#locking`.

## The format

A playbook project's `alai.toml` and the lock `alai lock` writes for it:

```toml
# alai.toml
link_mode = "hardlink"                   # settings: not part of the lock

[[index]]
name = "internal"
url = "https://ansible-index.corp.example/"

[project]
collections_dir = "collections"          # a project-only setting: not part of the lock either
requires_ansible = ">=2.17"
collections = ["community.general>=9,<11", "ansible.windows", "corp.tools>=1.2"]

[project.groups.test]
collections = ["ansible.posix"]

[project.overrides]
"ansible.netcommon" = ">=6"
ignore_requires_ansible = ["corp.tools"]

[project.sources]
"corp.tools" = { index = "internal" }
```

```toml
# alai.lock
# This file is generated by `alai lock`. Don't edit it by hand: any changes,
# comments included, are lost the next time alai writes it.
version = 1

[overrides]
"ansible.netcommon" = ">=6"
ignore_requires_ansible = ["corp.tools"]

[sources]
"corp.tools" = { index = "internal" }

[project]
requires_ansible = ">=2.17"
requirements = ["community.general>=9,<11", "ansible.windows", "corp.tools>=1.2"]
groups.test.requirements = ["ansible.posix"]

[[collection]]
name = "ansible.netcommon"
version = "8.7.1"
source = { index = "https://ansible-index.corp.example/" }
cksum = "3b1f…"
size = 1204812
requires_ansible = ">=2.16.0"
dependencies = ["ansible.utils"]

[[collection]]
name = "community.general"
version = "10.7.2"
source = { index = "https://index.alai.sh/" }
cksum = "5459…"
size = 2913455
requires_ansible = ">=2.16.0"
dependencies = ["community.library_inventory_filtering_v1"]

[[collection]]
name = "corp.tools"
version = "1.4.0"
source = { index = "https://ansible-index.corp.example/" }
cksum = "e1fb…"
size = 84213
requires_ansible = ">=2.15,<2.18"        # ignored for corp.tools, as alai.toml asks
dependencies = ["ansible.netcommon"]

# ...ansible.posix, ansible.utils, ansible.windows and
# community.library_inventory_filtering_v1 the same way
```

| Key | |
|---|---|
| `version` | The lockfile format. A lock with a higher `version` than this alai reads is an error asking for a newer alai |
| `overrides` | `alai.toml`'s `[project.overrides]`, as written: one set for the whole resolution |
| `sources` | `alai.toml`'s `[project.sources]`, as written (index names, not URLs): also resolution-wide |
| `project` | The project as a root of the resolution: its `requires_ansible`, `requirements` (`alai.toml`'s `project.collections`) and `groups.<name>.requirements`, as written |
| `collection` | One entry per locked collection, sorted by name |
| `collection.name`, `.version` | What's installed |
| `collection.source` | Where it comes from, as a table naming the kind. Only `{ index = "<index root URL>" }` today |
| `collection.cksum`, `.size` | The artifact's sha256 and size, from the index |
| `collection.requires_ansible` | The version's own `requires_ansible`, as the index gives it; absent when it has none |
| `collection.dependencies` | The names of the locked collections it depends on, sorted |

What `alai sync` installs is the closure of the roots' requirements, through
each entry's `dependencies`, plus the groups asked for. A root needs no
`dependencies` of its own: every requirement names a collection, so its
direct dependencies are its requirements' names.

### A collection project (planned)

When collection repositories are supported (see
[collection-development.md](collection-development.md)), the collection
itself is the root, as a uv project is an entry with `source = { editable =
"." }`:

```yaml
# galaxy.yml
namespace: corp
name: tools
version: 1.4.0
dependencies:
  ansible.netcommon: ">=5.0.0"
  ansible.utils: "*"
```

```yaml
# meta/runtime.yml
requires_ansible: ">=2.16"
```

```toml
# alai.toml: what galaxy.yml and meta/runtime.yml can't say. A [project] with
# requires_ansible or collections would override them.
[project.groups.test]
collections = ["ansible.posix", "community.crypto>=2"]

[project.overrides]
"ansible.netcommon" = ">=6"
```

```toml
# alai.lock
version = 2

[overrides]
"ansible.netcommon" = ">=6"

[[collection]]
name = "corp.tools"
version = "1.4.0"                                          # galaxy.yml
source = { project = "." }                                 # the checkout, linked into the test tree
requires_ansible = ">=2.16"                                # meta/runtime.yml
requirements = ["ansible.netcommon>=5.0.0", "ansible.utils"]   # galaxy.yml's dependencies
groups.test.requirements = ["ansible.posix", "community.crypto>=2"]

[[collection]]
name = "ansible.netcommon"
version = "8.7.1"
source = { index = "https://index.alai.sh/" }
# ...
```

There's no `[project]`: the root is the entry whose source is `project`,
which has `requirements` rather than `dependencies`, and no `cksum`, since it
changes with every edit. `lock --check` compares each of its inputs with the
file it came from. `galaxy.yml`'s mapping becomes requirement strings, with
`"*"` dropped. The format becomes `2`, so an alai that only knows playbook
projects refuses the lock rather than misreading it. A workspace of several
collections is the same with several `project` sources (`{ project =
"collections/corp/tools" }`), sharing one `[overrides]`, and the resolution's
`requires_ansible` is the roots' ranges combined, as uv combines its
members' `requires-python`.

## Decisions

- **TOML, named `alai.lock`, beside `alai.toml`**, as `uv.lock` and
  `Cargo.lock` are. It's committed with the project.
- **Written deterministically**: collections sorted by name, dependencies
  sorted, one key per line in a fixed order, so a change shows up as a small
  diff. A comment at the top says it's generated.
- **Written by our own emitter**, not a TOML library. The stdlib only reads
  TOML, and tomli-w can't write `source` as an inline table or give control
  over the layout; the schema is small and alai writes all of it. Tests read
  every written lock back with `tomllib`.
- **Each root's inputs are copied in**, so `alai sync` can tell the lock
  is out of date without resolving, and `lock --check` can tell the inputs
  changed even when the result didn't. They're
  compared after parsing (`Manifest.resolution_key`), so whitespace or
  reordering in `alai.toml` doesn't make the lock stale; requirements compare
  as sets.
- **`alai lock`** loads the settings and `alai.toml`, resolves with the
  current `alai.lock` as the preference, and writes the lock atomically, as
  `uv lock` does. An unchanged result leaves the file untouched, and a failed
  resolution leaves the lock untouched. `-U` / `--upgrade` and `-P` /
  `--upgrade-package NAME` drop the locked preference for every collection
  or the named ones, as uv's flags of the same names.
- **`alai lock --check` resolves**, as `uv lock --check` does, and exits 1
  without writing when the lock is missing (checked first, without
  resolving) or would change: its copied inputs ask for something else than
  `alai.toml`, or the resolved collections differ, say because a locked
  version was removed from its index or its index is no longer configured.
  The change lines are printed as `alai lock` would print them. It connects
  to the indexes unless `--offline`. A check that only compared the files,
  without the network, was the first version (2026-10-20) and was dropped
  to follow uv: it couldn't see a removed version. That comparison stays as
  `_lock.stale()` for `sync`, which needs to decide quickly whether to
  resolve again.
- **Roots and the resolution are kept apart**, as uv does: a root's
  requirements, groups and `requires_ansible` are on the root (`[project]`
  today, `project`-source collections later), and the overrides for the
  whole resolution are `[overrides]`. `alai.toml` makes the same split:
  everything under `[project]` is the project, and `[project.overrides]`
  is only read from the root `alai.toml` once workspaces exist.
- **The project is `[project]`, not a `[[collection]]`**: a playbook project
  isn't a collection, has no name and is never installed. Kinds of thing
  have their own tables (`[[collection]]`, later `[[role]]`) rather than one
  `[[package]]` with a `type`, because a role and a collection can share a
  `namespace.name`, as Ansible's own split (`requirements.yml`'s
  `collections:` and `roles:`, `collections/` and `roles/`) reflects. `project` is a
  kind of source, so it can't collide with a collection's name.
- **One resolution for every group**, as uv does: `project.collections` and
  all `[project.groups.*]` are resolved together into one consistent set, and `sync`
  installs the groups asked for. Which collections a group needs is worked
  out from the manifest and each entry's `dependencies`, so the lock doesn't
  record group membership. A group that conflicts with the project fails
  `lock`.
- **The index is recorded by URL**, not by the name `alai.toml` gives it, so
  renaming an index doesn't change the lock and two people with different
  names for one index agree. `lock --check` also fails when an entry's index
  URL is no longer configured.
- **No download URLs.** `sync` builds them from the index's `dl` template
  and `cksum`, as Cargo does, so moving the artifact host doesn't invalidate
  locks. The index spec's client rules ask lock files to record the index,
  name, version and `cksum`; `size` lets `sync` report download sizes before
  it starts.
- **Dependencies are names.** A name has exactly one entry in a lock (one
  version per collection per environment), so the name says which. uv does
  the same: a plain `uv.lock` references a dependency as `{ name = "demo" }`,
  and only adds `version`, `source` and `marker` when the lock holds two
  entries for one package, as a forked resolution does (tested with uv 0.13:
  `demo==1.0; python_version < "3.12"` and `demo==2.0; python_version >=
  "3.12"` gave two `[[package]]` entries named `demo`, each with
  `resolution-markers`, and references carrying all three). Collections have
  no platforms, Python-version wheels or conditional dependencies, so the only
  marker alai would ever need is the ansible-core version, for the "forks"
  option in [environments.md](environments.md). If locks fork,
  `dependencies` becomes tables (`name`, plus `version` and `marker` when
  ambiguous) and entries get their ansible-core range, behind a `version`
  bump: an alai that doesn't know forks must refuse such a lock, which
  today's reader already does ("locked more than once").
- **`requires_ansible` per entry** lets `sync` and `run` warn when the
  installed ansible-core is outside a locked collection's range, including
  upper bounds the resolver ignored (see [resolver.md](resolver.md)).
- **Unknown keys are ignored when reading**, as in the index spec, so a
  newer alai can add an optional key without breaking older ones in the same
  team. `version` is bumped only for a change an older alai would misread,
  such as a new `source` kind; an unknown kind is an error asking for a
  newer alai.

## Planned: other sources

Local directories (including editable installs) and git repositories, through
the planned `[sources]` table in `alai.toml`. They change the lock in three
ways, which is why `source` is a table naming its kind now:

```toml
[[collection]]
name = "corp.tools"
version = "1.4.0"
source = { git = "https://github.com/corp/tools.git", rev = "v1.4.0", commit = "3f9a1c07…" }
dependencies = ["community.general"]

[[collection]]
name = "corp.dev"
version = "0.1.0"
source = { path = "../corp.dev", editable = true }
dependencies = []
```

- **What pins the content depends on the source.** An index or tarball URL
  has `cksum`; git has the commit (with the requested `rev`, so
  `--upgrade` can move a branch); a local path has nothing, since it's
  meant to change. `cksum` becomes optional per kind.
- **Mutable sources keep a snapshot of their metadata.** The `version` and
  `dependencies` of a git or path collection come from its `galaxy.yml` at
  lock time; `lock --check` and `sync` re-read it and report the lock out of
  date when they've changed, as uv does for local packages.
- **Their dependencies are chosen like top-level requirements** (a pinned
  index, else the first index that has them): the index spec's rule that
  dependencies come from their parent's index can't apply to a collection
  that has no index.

Only the project's own manifest can name these sources. A `galaxy.yml` lists
dependencies by name and version only, so a dependency can't pull in a git
URL or a local path, as uv's `[tool.uv.sources]` isn't transitive either.

Paths in the lock are relative to the project root. Installing:

- **A git source is built, as ansible-galaxy builds one.** Its
  `install_src` reads `galaxy.yml`, drops what `build_ignore` and the
  `manifest` directives exclude, writes `MANIFEST.json` and `FILES.json`,
  and copies the rest. ansible-galaxy only treats a directory as an
  installed collection with a `MANIFEST.json` (`_is_installed_collection_dir`:
  "A MANIFEST.json is expected if the collection has been built and
  installed via ansible-galaxy"), and ansible-test reads the version from it.
  Copying the checkout as it is would load in ansible-core, but look unlike
  an installed collection to everything else and bring development files
  along. The build is cached by commit.
- **An editable path is linked as it is**, with no build: the point is to
  edit the source. The link is a symlink in `ansible_collections` to the
  checkout, and its target is what says it's installed, as uv's `.pth` and
  `direct_url.json` do for an editable package; replacing or removing it
  only unlinks it ([install.md](install.md)). That leans on the debugging
  requirement in
  [collection-development.md](collection-development.md).
